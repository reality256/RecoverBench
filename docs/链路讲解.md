## 1. 全局图景:这个系统里有"谁"

先分清一件事:**哪些程序跑在"你的 Windows"上,哪些跑在"容器"里**。这是新手最容易混淆的地方。

```
你的电脑 (Windows)
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  跑在 Windows 上的(直接被你命令行启动):                     │
│    curl                  ← 发 HTTP 请求测试               │
│    scripts/inject_fault.py  ← 注入故障                    │
│    scripts/reset_env.py     ← 恢复环境                    │
│    evaluator/evaluate.py    ← 判定 PASS/FAIL              │
│                                                          │
│  ┌─────────── Docker Desktop 内部(WSL2 Linux)──────────┐ │
│  │                                                     │ │
│  │  跑在容器里的:                                       │ │
│  │   ┌─────────────────┐        ┌─────────────────┐    │ │
│  │   │ api 容器         │  TCP   │ redis 容器       │    │ │
│  │   │ uvicorn          │───────▶│ redis-server    │    │ │
│  │   │ FastAPI 应用      │        │ 监听 6379 端口   │    │ │
│  │   │ 监听 8000 端口    │        └─────────────────┘    │ │
│  │   └─────────────────┘                                │ │
│  │   两个容器连在同一个虚拟网络 recoverbench_default 上     │ │
│  └─────────────────────────────────────────────────────┘ │
│                                                          │
│  Windows 的 localhost:8000 由 Docker Desktop 转发进 api 容器 │
└──────────────────────────────────────────────────────────┘
```

整个项目就是在制造一个**有依赖关系的系统**:

```
api 依赖 redis。redis 活着 → api 正常;redis 挂了 → api 降级。
```

- 有人负责**搞坏它**(inject_fault)
- 有人负责**修好它**(reset_env,将来是 Agent)
- 有人负责**客观判定修没修好**(evaluator)

这就是 benchmark(基准测试)的本质:一套可重复的"出题—答题—判卷"环境。

## 2. 概念速通:进程 / 端口 / TCP / HTTP

这四个词后面会反复出现,先花一分钟过一遍。

| 概念 | 一句话解释 | 类比 |
|---|---|---|
| **进程** | 一个正在运行的程序 | 一个正在上班的人 |
| **端口** | 进程对外提供服务的"门牌号"(0~65535) | 公司分机号:8000 是 api 的前台,6379 是 redis 的前台 |
| **TCP 连接** | 两个程序之间建立的一条"专线电话" | 打电话:先拨号(连接),再说话(传数据),挂断(断开) |
| **HTTP** | 在 TCP 之上的"寄信格式":请求+响应 | 寄信:写明地址(GET /health)和收件人,收到回信(200/503 + JSON) |

**HTTP 状态码**记住两类就够用:

- `200` = 成功;`404` = 没找到;`503` = 服务不可用
- `2xx` 一切正常,`5xx` 服务器这边出了问题

## 3. Docker 入门

### 3.1 为什么需要 Docker

你的 api 需要:Python 3.12 + 安装 fastapi/redis/uvicorn + 旁边还得跑着一个 redis-server。
如果直接在你自己电脑上装这些东西,换台电脑就全要重来,而且版本不一致时出各种玄学问题("在我电脑上能跑")。

Docker 的思路:**把"应用 + 它需要的所有依赖"打包成标准件**,任何装了 Docker 的机器都能原样跑起来。这个标准件叫**镜像(image)**。

### 3.2 镜像 vs 容器(必须分清)

| | 镜像 image | 容器 container |
|---|---|---|
| 是什么 | 打包好的只读模板(文件系统快照) | 镜像**运行起来**后的实例 |
| 类比 | 程序安装包 / 光盘 | 装好后正在运行的程序 |
| 数量 | 一个 | 同一镜像可以跑出无数个容器 |

Docker Desktop 就像一台"虚拟机里的主机",容器就是上面运行的进程(严格说容器共享内核,不是完整虚拟机,但入门这么理解足够)。

> Windows 上的小知识:Docker Desktop 内部有一个 WSL2 的 Linux 虚拟机,容器实际跑在那里面。你不用关心它,只要知道 `localhost:8000` 会被 Docker Desktop 自动转发进容器。

### 3.3 Dockerfile:镜像的"菜谱"

你项目里的 `Dockerfile`:

```dockerfile
FROM python:3.12-slim          # 基础镜像:自带 Python 3.12 的精简版 Linux
WORKDIR /app                   # 设定工作目录(相当于 cd /app,不存在会自动建)
COPY requirements.txt .        # 把宿主机文件拷进镜像
RUN pip install -r requirements.txt   # 构建镜像时执行:装依赖
COPY app ./app                 # 把应用代码拷进镜像
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
                               # 容器启动时执行:跑起 web 服务
```

关键区分两个指令:

- **`RUN`**:构建镜像时执行一次,结果"烧"进镜像(比如装好的依赖)
- **`CMD`**:容器**每次启动**时执行(比如跑服务)。一个 Dockerfile 只有一条 CMD

`docker compose up --build` 时,就是照着这份菜谱做菜(构建镜像)。

### 3.4 compose.yaml:一次编排多个容器

单容器用 Dockerfile 就够了,但你的系统有 **两个** 容器(api + redis)要一起启动、连在同一个网络上。`compose.yaml` 就是用来描述"这个系统由哪些容器组成":

```yaml
services:                 # 两个"服务"= 两个容器

  api:
    build: .              # 这个服务的镜像不用下载,用当前目录的 Dockerfile 现做
    ports:
      - "8000:8000"       # 端口映射:宿主机的8000 → 容器的8000
                          # 所以你在 Windows 上访问 localhost:8000 就能打到容器里
    depends_on:
      - redis             # 启动顺序:先 redis 后 api

  redis:
    image: redis:7        # 这个服务直接用现成镜像,从镜像仓库下载
```

两个重要概念:

1. **端口映射 `8000:8000`**:容器在网络上是与外界隔离的,它内部的 8000 端口默认只有容器自己知道。这行把"宿主机的 8000"接到"容器的 8000",相当于给容器开了扇门。
   注意 redis 没写 ports —— 所以 redis 的 6379 **只有同网络的容器能连,你 Windows 上连不到**。这是故意的:生产环境里数据库通常不直接暴露。

2. **depends_on 只是"启动顺序"**,不是"等它就绪"。如果 api 启动太快而 redis 还没准备好,api 也会报错(本项目简单,基本不会遇到;但要知道这个概念,以后复杂系统会靠 healthcheck 解决)。

### 3.5 Docker 网络:为什么代码里写 `host="redis"` 就能连上

compose 启动时自动创建了一个虚拟网络 `recoverbench_default`,两个容器都在里面。

在这个网络里,**每个服务名会被当成"主机名"来用**。api 容器里写 `redis`,会被 Docker 内嵌的 DNS 翻译成 redis 容器的地址。

所以 `app/main.py` 里:

```python
r = redis.Redis(host="redis", ...)
```

这个 `"redis"` 不是随便起的 —— 它是 `compose.yaml` 里的**服务名**。如果服务名改成 `mydb`,代码里就要写 `host="mydb"`。

> 我们在调试时见过这个机制的反面:redis 容器被 stop 之后,`"redis"` 这个名字在 DNS 里查不到了,要花约 4 秒才返回"查无此名"。这就是为什么降级响应要 3~4 秒 —— 剩下的时间是 TCP 与 DNS 在帮你确认"它真的没了"。

### 3.6 常用命令速查

| 命令 | 作用 |
|---|---|
| `docker compose up -d --build` | 构建镜像并后台启动整个系统 |
| `docker compose ps` | 看各容器状态(Up / Exited) |
| `docker compose logs -f api` | 持续看 api 容器日志 |
| `docker compose stop redis` | 停掉 redis 容器(我们的"注入故障") |
| `docker compose start redis` | 启动已存在的 redis 容器(我们的"恢复") |
| `docker compose down` | 停止并删除整个系统的容器和网络 |
| `docker compose exec api sh` | "进入"api 容器,在里面开个终端 |
| `docker images` / `docker ps -a` | 看镜像列表 / 看所有容器 |

> 国内网络小注:Docker Hub 官方镜像仓库被墙,我们给 Docker Desktop 配了镜像加速站(在 `C:\Users\Lee\.docker\daemon.json` 的 `registry-mirrors`)。以后拉镜像慢或失败,先想到这个。

## 4. Redis 入门

### 4.1 Redis 是什么

一个**内存里的 key-value 数据库**:

- 数据存在内存里,所以极快(我们的场景下毫秒级响应)
- 格式就像一个大字典:`键 → 值`,比如 `"name" → "recoverbench"`
- 最常用作**缓存**:把热数据放在 Redis,应用就不用每次查慢数据库

### 4.2 它在这个项目里是什么角色

不复杂 —— 你的 api 只用它做两件事:

1. `ping()`:问一句"你还活着吗?"(检查连通性)
2. `get(key)`:按 key 取一个值(取缓存)

**它在项目里最重要的角色不是"存数据",而是"被依赖"。**
整个 benchmark 的因果链就是:

```
redis 活着 → /health 返回 healthy
redis 挂了 → /health 返回 degraded,/cache 返回 503
```

### 4.3 app 是怎么连上它的

`app/main.py` 开头那一大段参数,是这次工程实践里最值得学的东西之一:

```python
r = redis.Redis(
    host="redis",              # 主机名 = compose.yaml 里的服务名
    port=6379,                 # Redis 默认端口
    decode_responses=True,     # 返回值解码成 str(否则是 bytes)
    socket_connect_timeout=1,  # 建立 TCP 连接最多等 1 秒
    socket_timeout=1,          # 单次读写最多等 1 秒
    health_check_interval=1,   # 从连接池取连接前,若闲置超 1 秒先 PING 探活
    retry=Retry(NoBackoff(), 0)  # 失败不重试,立刻抛异常
)
```

### 4.4 连接池,以及"僵尸连接"

TCP 连接是有开销的(每次握手都耗时)。如果每个请求都新建连接,性能会很差。
所以 redis-py 内部有个**连接池**:连接用完不销毁,放回池子里,下次复用 —— 就像公共自行车。

但复用有个坑:池子里的连接可能**已经死了**,而客户端并不知道(对方停机不一定通知你)。
这时候一个请求写进死连接,如果**没有读超时**,就会一直等响应等到天荒地老。

我们在 `main.py` 里的三道防线就是对付它的:

| 参数 | 防什么 |
|---|---|
| `socket_connect_timeout=1` | 连不上(对方不存在)→ 1 秒后放弃 |
| `socket_timeout=1` | 连上了但对方不回应(僵尸连接)→ 1 秒后放弃 |
| `health_check_interval=1` | 每次取连接前主动探活,发现死连接就换新的 |

### 4.5 超时 vs 重试:分布式系统的第一课

设了超时还不够。新版 redis-py(8.x)默认的**重试策略是:失败后重试 10 次,指数退避**(每次等待时间翻倍)。

于是真实延迟 = 超时 × (1 + 重试次数) + 退避等待 ≈ **43 秒**。

所以我们的配置里加了一句:

```python
retry=Retry(NoBackoff(), 0)   # 不重试,失败立即抛异常
```

**这是基准环境的硬需求:故障必须"快速、确定地"暴露出来。**
不然每次注入故障后,系统都要卡 43 秒,agent 和 evaluator 全被拖死。

### 5.1 `app/main.py` —— 被测系统

```python
from fastapi import FastAPI, HTTPException
import redis
from redis.backoff import NoBackoff
from redis.retry import Retry

app = FastAPI()          # 创建应用实例

# Redis 客户端(参数含义见 4.3 节)
r = redis.Redis(...)

@app.get("/health")      # 装饰器:把下面函数注册为 "GET /health" 的处理函数
def health():
    try:
        r.ping()         # 探活
        return {"status": "healthy", "redis": "healthy"}
    except Exception:    # 任何异常(ping 超时、连不上)都走这里
        return {"status": "degraded", "redis": "unavailable"}

@app.get("/cache/{key}") # {key} 是"路径参数":GET /cache/foo 时 key="foo"
def get_cache(key: str):
    try:
        value = r.get(key)
        return {"key": key, "value": value}
    except Exception as e:
        raise HTTPException(status_code=503, detail=f"Redis unavailable: {str(e)}")
        # 主动抛 503:告诉调用方"我依赖的东西挂了"
```

两个接口的设计差异值得注意:

- `/health` 是**探测接口**:哪怕 Redis 挂了也返回 200,只是内容变成 `degraded`。它的意义就是"让我随时能问系统状态"。
- `/cache` 是**业务接口**:依赖 Redis 才能干活,挂了就直接 503。

`uvicorn` 是什么?FastAPI 只是"写接口"的框架,它自己不监听网络端口。
**uvicorn** 是 ASGI 服务器,负责收 HTTP 请求、转给 FastAPI、把结果发回去。
Dockerfile 里的 `CMD` 就是让容器一启动就运行 uvicorn,跑在 8000 端口。

### 5.2 `scenarios/redis_down.yaml` —— 把事故变成数据

```yaml
id: redis_down_001        # 事故编号
description: ...          # 人类可读的描述
fault:                    # 故障是什么
  type: service_down
  target: redis
expected:
  root_cause: redis_unavailable   # 标准答案:根因
success:                  # 什么状态算"修好了"
  api_health: healthy
  redis_health: healthy
timeout_seconds: 120      # 限时
```

YAML 就是一种"数据格式"(像 JSON,但更像给人写的)。
这一步的意义:**以后加新故障(CPU 打满、配置改坏),只要加一个 yaml 文件,不用改代码**。这叫做"把可变的东西从代码里抽出来变成数据"。

### 5.3 `scripts/inject_fault.py` —— 用 Python 当 Docker 的"遥控器"

```python
import subprocess

def inject_redis_down():
    subprocess.run(["docker", "compose", "stop", "redis"], check=True)
    # 相当于你在终端敲: docker compose stop redis
    # check=True:如果命令失败(比如 redis 容器不存在),立刻抛异常

if __name__ == "__main__":
    inject_redis_down()
```

`subprocess.run` = **在 Python 里执行一条终端命令**,并等它执行完。

为什么不直接手敲 `docker compose stop redis`?
因为手敲是"人工操作",无法被**别的程序调用**。写成脚本后:

- 你跑 `python scripts/inject_fault.py` 是注入故障
- 将来实验框架跑它,也是注入故障
- Agent 想注入故障?也可以调它

脚本化 = 可重复 = 可自动化。这是工程化的核心习惯。

`reset_env.py` 同理,只是执行 `docker compose start redis`。
注意 `stop` 和 `start` 是一对:容器停止后**还在**(只是不运行),start 能把它重新拉起来。`docker compose down` 才是"删除"。

### 5.4 `evaluator/evaluate.py` —— 裁判

```python
import requests

def evaluate():
    try:
        response = requests.get("http://localhost:8000/health", timeout=2)
        data = response.json()
        if data["status"] == "healthy" and data["redis"] == "healthy":
            return True
    except Exception:
        pass       # 连不上/超时/格式不对,统统算失败
    return False

if __name__ == "__main__":
    print("PASS" if evaluate() else "FAIL")
```

这是整个项目**最重要的一个文件**,因为它定义了"真相"(ground truth):

> **Agent 说"我修好了"不算数。环境状态才算数。**

注意一个细节:它跑在你的 Windows 上,通过 `localhost:8000` 走 Docker 的端口映射去查容器里的服务。所以 evaluator 完全独立于被测系统 —— 它不信任任何人的说法,只信自己亲自探到的结果。

### 5.5 `agent/` —— 未来的"答题者"(现在是空的)

steps.md 的设计里,将来 Agent 只能使用几个**受限工具**(不给它随意执行 shell 命令的权限):

```
get_api_health()          # 观察:API 健康吗
get_service_status(service)   # 观察:某个服务状态(白名单:api / redis)
get_service_logs(service)     # 观察:看日志(tail 限 1~100,有字符数上限)
start_service(service)        # 行动:启动已停的服务(V1 只允许 redis)
verify_api()              # 内部辅助:验证修好没有(不暴露给模型)
```

工具返回统一协议 `{"ok", "data", "error"}`,参数校验失败绝不执行命令。
观察 → 诊断 → 行动 → 验证,而不是"随便跑 Linux 命令"。这对应真实运维里的权限分级。
决策由**策略**(`agent/policies/`)负责,执行和记账由**公共循环**(`agent/loop.py`)负责 —— 以后换成 LLM 策略时,工具执行、日志、步数预算共用同一套代码。

**四层结构**(V1 之后):

```
策略(选下一步)  →  循环(记账/预算/轨迹)  →  分发器(四道检查)  →  工具(真正干活)
rule.py / llm.py    loop.py                dispatch.py          tools.py
```

- **分发器**:工具存在?参数类型范围对不对?服务在白名单里?预算还有吗?四道全过才执行。
- **预算**:工具 10 次 / 环境修改 2 次 / 整轮 120 秒(单调时钟)。**非法调用也消耗预算** ——
  这样策略(尤其是模型)一直输出无效参数时,循环一定会结束。
- **轨迹**:每次运行写 `runs/<run_id>/{config.json, trace.jsonl, result.json}`,
  只用运行目录就能还原"看到了什么、做了什么、为什么结束"。

## 6. 完整跑一次:链路走查

把整个闭环的时间线串起来看。每一步,"谁"在哪里干什么:

### 第 0 步:`docker compose up -d --build`

1. compose 读取 `compose.yaml`
2. api 服务要 `build: .` → 按 Dockerfile 做菜:下载 python:3.12-slim 基础镜像 → 装依赖 → 拷代码,得到 api 镜像
3. redis 服务直接下载 redis:7 镜像
4. 创建虚拟网络 `recoverbench_default`
5. 先启动 redis 容器,再启动 api 容器
6. api 容器启动时执行 CMD:uvicorn 在容器内 8000 端口监听
7. Docker Desktop 把 Windows 的 8000 端口接到 api 容器

### 第 1 步:访问 `http://localhost:8000/health`(healthy)

```
curl(Windows)
   │ HTTP GET /health
   ▼
Windows 的 8000 端口
   │ Docker Desktop 端口映射
   ▼
api 容器内 uvicorn(8000)
   │ 转交给
   ▼
FastAPI → 匹配路由 → health() 函数
   │ r.ping() 需要连 Redis
   ▼
redis-py 建立 TCP 连接(目标:"redis" 主机名 → DNS → redis 容器 → 6379 端口)
   │ 发送 PING 命令
   ▼
redis-server 回应 PONG
   │ 原路返回
   ▼
FastAPI 组装 JSON:{"status":"healthy","redis":"healthy"}
   │ HTTP 200
   ▼
curl 打印结果(实测约 5 毫秒)
```

### 第 2 步:`python scripts/inject_fault.py`(注入故障)

1. Windows 上的 Python 执行 `docker compose stop redis`
2. Docker 给 redis 容器发停机信号,redis-server 退出
3. 容器状态变成 `Exited`;**它和 api 之间已有的 TCP 连接断开(或变成僵尸)**

### 第 3 步:再访问 `/health`(degraded)

1. 请求照常进到 `health()` 函数
2. `r.ping()`:
   - 连接池里的旧连接已死 → 探活发现 → 换新连接
   - 新建连接:查 DNS(`"redis"` 已不存在,约 4 秒确认)→ 连接失败
   - 重试已关 → 1 秒超时内立刻抛异常
3. 异常被 `except` 捕获 → 返回 `{"status": "degraded", "redis": "unavailable"}`
4. 总耗时约 3.5 秒 —— **故障被快速、确定地暴露出来**

### 第 4 步:`python scripts/reset_env.py`(恢复)

1. `docker compose start redis` → redis-server 重新起来
2. 下次请求时,连接池探活发现旧连接仍死 → 建新连接 → 成功
3. `/health` 回到 healthy(约 5 毫秒)

### 第 5 步:`python evaluator/evaluate.py`(判卷)

1. evaluator 自己发请求探 `/health`
2. 得到 `healthy` + `healthy` → 输出 `PASS`

**这就是整个链路。** 出题(注入)、环境响应(降级)、恢复、判卷,四个环节全部脚本化,换任何人、任何时间跑,结果一致 —— 这就是"可重复的 benchmark"。

## 7. 你踩过的两个坑(复盘)

调试是工程能力里最值钱的部分。回头看这两个坑,记住的不是答案,而是**定位方法**。

### 坑 1:僵尸连接 + 没有读超时 → 请求挂起

- **现象**:Redis 挂掉后,`/health` 秒回 degraded,但 `/cache/test` 卡住不动。
- **定位方法**:分步测量。进容器单独测 DNS(4 秒)、单独测一次 ping(44 秒),把 43 秒归因到"某一步在重复执行"。
- **原因**:`socket_connect_timeout` 只管"建立连接",管不住"往旧连接里写然后等回复"。连接池里的旧连接已死,写入成功但永远等不到响应。
- **修复**:`socket_timeout=1`(读超时)+ `health_check_interval=1`(用前探活)。

### 坑 2:redis-py 8.x 默认重试 10 次 → 43 秒

- **现象**:加了超时后反而**更慢更一致**了,每次都是 43 秒。
- **定位方法**:查版本(8.1.0)→ 看默认配置(`Retry` 对象里 `_retries: 10`,指数退避)。
- **原因**:一次命令 = 11 次尝试 × 每次 4 秒 DNS ≈ 44 秒。超时管单次,**重试管总时长**,两者要一起考虑。
- **修复**:`retry=Retry(NoBackoff(), 0)`,失败立即暴露。

### 方法论总结

> 遇到"卡住/超时"类问题,永远先问:**时间花在哪一步了?**
> 分步计时(打印 elapsed)比盯着代码猜快十倍。
