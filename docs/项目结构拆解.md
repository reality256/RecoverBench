## 1. 一句话理解整个项目

> **Docker 里跑着一个会坏的网站(环境),一个程序去修它(Agent),另一个程序独立检查修好没有(裁判)。**

三个角色必须**互相独立**:

| 角色 | 谁 | 住在哪 |
|---|---|---|
| 环境 | FastAPI 服务 + Redis | Docker 容器里 |
| Agent | 规则 或 大模型 | 你的 Python 进程 |
| 裁判 | evaluator | 你的 Python 进程(但和 Agent 不通信) |

---

## 2. 三层世界

```
第 1 层:环境(Docker 容器)—— 被修的对象
┌───────────────────────────────────────────────┐
│   api 容器                 redis 容器          │
│   app/main.py  ──TCP──▶   redis-server        │
│   (FastAPI 服务)          (数据服务)           │
│   由 compose.yaml 定义,用 Dockerfile 构建       │
└───────────────────────────────────────────────┘
                    ▲  ▲
        HTTP 请求    │  │  docker 命令
                    │  │
第 2 层:Agent(修理工)                          │
┌───────────────────────────────────────────────┐
│  tools.py 提供 4 个受限工具(唯一能碰环境的入口)  │
│  dispatch.py 检查"能不能执行"                   │
│  loop.py 负责"跑循环、记账、写日志"              │
│  policies/ 决定"下一步干什么"(规则 or 模型)      │
└───────────────────────────────────────────────┘
                    │
                    │ 写运行轨迹
                    ▼
              runs/<id>/
                    ▲
                    │ 读轨迹 + 自己探测环境
第 3 层:裁判(验收员)
┌───────────────────────────────────────────────┐
│  evaluator/evaluate.py:自己发 HTTP 请求验证      │
│  "健康 + 业务数据正确,连续 3 次"才算 PASS         │
└───────────────────────────────────────────────┘
```

**关键**:Agent 和裁判**不互相调用**。Agent 只写轨迹,裁判只看环境 + 把结论附到轨迹里。

## 3. 完整依赖图

箭头 `→` = "import 或调用"。这张图是按真实代码扫描出来的:

```
                     ┌─────────────────────────────┐
                     │   scripts/run_benchmark.py   │  ← 实验总入口
                     │   (唯一的"总指挥")            │
                     └──┬───────┬────────┬─────────┘
        读场景 yaml      │       │        │  用 subprocess 启动
      ┌─────────────────┘       │        └──────────────┐
      ▼                         │                       ▼
scenarios/*.yaml                │              agent/agent.py  ← 单次运行入口
                                │                       │
                  用 import 调用 │                       │ import
                                ▼                       ▼
                  ┌──────────────────────┐   ┌──────────────────────┐
                  │ evaluator/evaluate.py│   │   agent/loop.py      │
                  │  (独立裁判)           │   │  (循环 + 记账)        │
                  └──────────┬───────────┘   └───┬──────────────┬───┘
                             │                   │              │
                        HTTP │          import   │              │ import
                             ▼                   ▼              ▼
                   ┌──────────────────┐  ┌──────────────┐  ┌──────────────┐
                   │  app/main.py     │  │dispatch.py   │  │ budget.py    │
                   │  (被修的服务)     │  │(四道检查)     │  │ (预算)        │
                   └────────┬─────────┘  └──────┬───────┘  └──────────────┘
                            │                   │
                       TCP  │                   │ 调用
                            ▼                   ▼
                   ┌──────────────────┐  ┌──────────────┐
                   │  redis-server    │  │  tools.py    │
                   │  (数据服务)       │  │ (4 个受限工具) │
                   └──────────────────┘  └──────┬───────┘
                                                │
                                    HTTP /health │ docker compose
                                                ▼
                                         (回到环境)

     loop.py 还要用:
       ├── trace.py  → 写 runs/<id>/{config,trace,result}.json
       └── policies/ → 问"下一步干什么"
              ├── rule.py        (规则,不联网)
              └── llm.py ──▶ llm_client.py ──▶ DeepSeek API
                              └── config.py (读 .env 拿 key)
```

**记住三条主线就够了**:

1. **修理工的路**:`agent.py → loop.py → policies/ → dispatch.py → tools.py → 环境`
2. **记账的路**:`loop.py → trace.py → runs/`
3. **验收的路**:`run_benchmark.py → evaluator → 环境`

## 4. 每个文件干什么

### 第 1 层:环境(4 个文件)

| 文件 | 作用 | 一句话 |
|---|---|---|
| `app/main.py` | 被测服务 | 50 行的 FastAPI:`/health` 探活、`/cache/{key}` 读缓存;**故意依赖 Redis** |
| `app/redis_client.py` | **空文件(占位)** | 建项目时留的坑,从没被用过,可以删 |
| `compose.yaml` | 容器编排 | 定义 api + redis 两个容器、端口映射、网络 |
| `Dockerfile` | api 镜像菜谱 | 装依赖 + 跑 uvicorn |

### 第 2 层:Agent(11 个文件)

**入口**

| 文件 | 作用 |
|---|---|
| `agent/agent.py` | **单次运行入口**。解析 `--policy rule/llm`,建预算和记录器,跑循环,打印结论和退出码 |

**核心四件套(每次运行都会用到)**

| 文件 | 作用 | 类比 |
|---|---|---|
| `agent/loop.py` | 循环:问策略 → 让分发器执行 → 记历史 → 写轨迹 → 查预算 | 车间主任:调度一切 |
| `agent/dispatch.py` | 四道检查:工具存在?参数对不对?服务白名单?预算够吗? | 门禁:谁能进、带什么进去 |
| `agent/tools.py` | **唯一能碰环境的代码**。4 个受限工具 + 统一返回格式 | 工人的手 |
| `agent/state.py` | 数据类型:`ToolCall`(调工具)、`Finish`(结束)、`HistoryEntry`(历史) | 通用零件 |

**决策(可替换的零件)**

| 文件 | 作用 |
|---|---|
| `agent/policies/rule.py` | **规则策略**:写死的 if/else,不联网、不需要 key |
| `agent/policies/llm.py` | **模型策略**:构造上下文 → 问模型 → 解析成"调工具"或"结束" |
| `agent/llm_client.py` | 只管发 HTTP 给 DeepSeek,收响应和用量,分类接口错误 |

**支撑**

| 文件 | 作用 |
|---|---|
| `agent/budget.py` | 预算账本:工具 10 次 / 修改 2 次 / 120 秒,单调时钟 |
| `agent/trace.py` | 写运行轨迹:`runs/<id>/` 三个文件 + 凭据脱敏 |
| `agent/config.py` | 读配置:`os.environ` → `.env` → 默认值 |

### 第 3 层:裁判(1 个文件)

| 文件 | 作用 |
|---|---|
| `evaluator/evaluate.py` | **独立验收**:发 HTTP 探测环境,连续 3 次健康+业务正确才 PASS |

### 场景数据(2 个文件)

| 文件 | 作用 |
|---|---|
| `scenarios/redis_down.yaml` | 故障定义:`fault.type = service_down, target = redis` |
| `scenarios/healthy.yaml` | 对照场景:`fault.type = none` |

> **设计要点**:加新故障 = 加一个 yaml,不改代码。runner 会读它们。

### 脚本(7 个)

| 文件 | 作用 | 你会用到的场合 |
|---|---|---|
| `scripts/run_benchmark.py` | **实验总入口**:一条命令重复 N 轮 | 跑对照实验 |
| `scripts/report_benchmark.py` | 汇总多次实验成一张表 | 出报告 |
| `scripts/inspect_run.py` | 查看某次运行的完整时间线 | 复盘"模型做了什么" |
| `scripts/check_llm.py` | 模型连通性体检(一次调用) | 换模型/key 时先跑它 |
| `scripts/run_e2e.py` | 冒烟验收(比 benchmark 轻) | 改完代码快速确认没断 |
| `scripts/run_llm_dryrun.py` | 用假模型跑真环境,**不花钱** | 验证链路但不消耗 API |
| `scripts/inject_fault.py` | 停掉 redis(手工注入故障) | 手动玩的时候 |
| `scripts/reset_env.py` | 启动 redis(手工恢复) | 手动玩的时候 |

### 测试(9 个文件,175 个用例)

| 文件 | 测什么 |
|---|---|
| `tests/test_tools.py` | 4 个工具(含 mock 掉 docker 和 HTTP) |
| `tests/test_dispatch.py` | 四道检查、预算扣减、超时注入 |
| `tests/test_budget.py` | 次数上限、时间预算、超时夹取 |
| `tests/test_trace.py` | 轨迹三文件、凭据脱敏 |
| `tests/test_agent.py` | RulePolicy 决策表 + 循环机制 |
| `tests/test_llm_client.py` | HTTP 请求构造、响应解析、错误分类 |
| `tests/test_llm_policy.py` | 上下文构造、决策解析、重试 |
| `tests/test_evaluator.py` | 判定逻辑、连续通过、退出码 |
| `tests/test_edge_cases.py` | **边界**:模型乱来、预算终止、谎报成功、无效实验 |
| `tests/test_report.py` | 报告分类与统计口径 |

> 测试是**唯一不碰真实环境的层** —— 全部用 mock 隔离,0.15 秒跑完。

### 配置与文档

| 文件 | 作用 |
|---|---|
| `.env` | **你的真实密钥**(已被 gitignore,永不提交) |
| `.env.example` | 模板(会被提交,**绝不能放真 key**) |
| `requirements.txt` | 依赖:fastapi / redis / uvicorn / requests |
| `README.md` | 怎么用 |
| `log.md` | 你的施工日志 |
| `steps.md` | ChatGPT 给的步骤(参考) |
| `docs/` | 学习文档 |

## 5. 两条主线走查

### 主线 A:跑一次模型 Agent

```
你敲:python agent/agent.py --policy llm
  │
  ├─ agent.py 解析参数 → config.py 读 .env 拿 key
  ├─ 建 Budget(预算账本)和 RunRecorder(轨迹记录器)
  ├─ 建 LlmPolicy(llm.py),带上 llm_client.py
  └─ 调 loop.py 的 run_loop()
        │
        └─ 循环 1~10 次:
             1. 问 llm.py:下一步干什么?
                  └─ llm.py 拼上下文(任务+拓扑+工具表+历史+预算)
                     └─ llm_client.py 发 HTTP 给 DeepSeek
                     └─ 模型回答:"调用 get_api_health"
             2. 把决定交给 dispatch.py
                  └─ 检查:工具存在?参数合法?预算够?
                  └─ 通过 → 调 tools.py
                       └─ tools.py 发 HTTP 或 docker 命令,碰到真实环境
             3. 结果记进 history,写进 trace.py → runs/<id>/trace.jsonl
             4. 模型说 finish(recovered) → 结束
  │
  └─ agent.py 写 result.json,打印结论和退出码
```

### 主线 B:跑一轮实验

```
你敲:python scripts/run_benchmark.py --policy llm --scenario redis_down --repeat 5
  │
  └─ 每轮:
       1. docker compose up -d          ← 恢复干净基线
       2. 等 /health 能响应
       3. docker exec redis-cli set 随机值  ← 预置业务数据
       4. 用 evaluator 的 probe() 验证基线
       5. 读 scenarios/redis_down.yaml → docker compose stop redis(注入)
       6. 验证注入真的生效(否则跳过本轮,记 setup_failed)
       7. subprocess 启动 agent/agent.py --run-id r1   ← 修理工上场
       8. 调 evaluator 的 evaluate()                    ← 验收员上场
       9. 把裁判结果附到 runs/<bench>/r1/result.json
      10. finally: 清理;清理失败就中止整个实验
  │
  └─ 写 summary.json → report_benchmark.py 读它出表
```

**注意第 5 步和第 7 步的区别**:runner 读 yaml 并调 docker(replay 权限),而 Agent 只能通过受限工具动手。**runner 能做的,Agent 不一定能做** —— 这是故意的权限设计。

## 6. 这些文件是什么时候长出来的

对照你的记忆,能更快找回位置:

| 阶段 | 新增文件 |
|---|---|
| **V0 环境**(Step 1-5) | `app/main.py`、`compose.yaml`、`Dockerfile`、`requirements.txt`、`scenarios/redis_down.yaml`、`scripts/inject_fault.py`、`scripts/reset_env.py`、`evaluator/evaluate.py` |
| **V0 Agent**(Step 6-7) | `agent/state.py`、`agent/tools.py`、`agent/agent.py`、`agent/__init__.py` |
| **V1 重构**(新 Step 2-5) | `agent/loop.py`、`agent/policies/rule.py`、`agent/policies/llm.py`、`agent/dispatch.py`、`agent/budget.py`、`agent/trace.py` |
| **接入模型**(Step 6) | `agent/config.py`、`agent/llm_client.py`、`.env`、`.env.example`、`scripts/check_llm.py`、`scripts/run_llm_dryrun.py` |
| **裁判升级 + Runner**(Step 7-8) | `evaluator/evaluate.py`(重写)、`scripts/run_benchmark.py`、`scenarios/healthy.yaml` |
| **验收**(Step 9) | `scripts/report_benchmark.py`、`tests/test_edge_cases.py`、`tests/test_report.py`、`docs/V1对照报告.md` |

**一句话理解这次膨胀**:V0 是"能修好"(3 个 Agent 文件),V1 是"能批量做实验并保证结论可信"(拆出循环/分发/预算/轨迹/报告)。**多出来的文件不是功能变多,而是把"可信"这件事做扎实了。**

## 7. 速查:出了问题该看哪个文件

| 症状 | 去看 |
|---|---|
| `/health` 返回 degraded | 环境问题 → `docker compose ps -a`、`app/main.py` |
| Agent 说修好了但环境没变好 | `runs/<id>/trace.jsonl`(它到底做了什么) |
| 模型请求失败 | `python scripts/check_llm.py`(先体检)、`.env` |
| 模型输出离谱(瞎调工具) | `agent/policies/llm.py` 的 `build_system_prompt()` |
| 工具被拒绝执行 | `agent/dispatch.py` 的 `ARG_SPECS`(参数表) |
| 循环停不下来 / 提前停了 | `agent/budget.py`(预算) |
| 裁判判错 | `evaluator/evaluate.py` 的 `probe()` |
| 实验某轮跑不起来 | `runs/<bench>/summary.json` 里的 `setup_failed` 原因 |
| 想看实验对比 | `python scripts/report_benchmark.py` |
| 改完代码怕改坏 | `python -m unittest discover -s tests`(0.15 秒) |

## 下一步的自然方向

现在的结构留好了三个扩展点:

1. **加故障场景** → 只加 `scenarios/xxx.yaml` + 在 `run_benchmark.py` 的 `inject()` 里加一个分支
2. **换决策策略** → 只写 `agent/policies/xxx.py`,实现 `decide(history, tools)` 一个方法
3. **加工具** → 在 `agent/tools.py` 写函数 + 在 `dispatch.py` 的 `ARG_SPECS` 登记参数表(有测试守着)
