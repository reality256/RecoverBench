# RecoverBench V1 对照报告

**日期**:2026-09-18 · **代码版本**:32ba664 · **模型**:deepseek-flash
**预算**(两个策略共用):工具 10 次 / 环境修改 2 次 / 整轮 120 秒

## 一、实验设置

| 项 | 内容 |
|---|---|
| 场景 | `healthy`(正常对照)、`redis_down`(Redis 被停止) |
| 策略 | `rule`(确定性规则)、`llm`(DeepSeek 模型决策) |
| 轮数 | 每种组合 5 轮,共 **20 轮**,顺序执行 |
| 每轮流程 | 重置基线 → 就绪 → 预置业务数据(随机值)→ 验证基线 → 注入故障 → 验证场景 → Agent → 独立裁判 → 保存 → 清理 |
| 评判标准 | 健康检查与业务读取(`/cache/{key}` 返回本轮预置值)**连续通过 3 次** |
| 有效性口径 | 基线/注入失败的轮次记为无效,**不进通过率分母** |

复现命令:

```bash
python scripts/run_benchmark.py --policy rule --scenario healthy    --repeat 5 --benchmark-id exp-rule-healthy
python scripts/run_benchmark.py --policy rule --scenario redis_down --repeat 5 --benchmark-id exp-rule-redis_down
python scripts/run_benchmark.py --policy llm  --scenario healthy    --repeat 5 --benchmark-id exp-llm-healthy
python scripts/run_benchmark.py --policy llm  --scenario redis_down --repeat 5 --benchmark-id exp-llm-redis_down
python scripts/report_benchmark.py exp-rule-healthy exp-rule-redis_down exp-llm-healthy exp-llm-redis_down
```

## 三、解读

### 两个通过率含义不同,必须分开读

- `healthy` 的 100% 代表**保持健康**:环境本来就是好的,Agent 不该乱动。两个策略都做到了 **0 次修改** —— 这是"不过度修复"的正向证据。
- `redis_down` 的 100% 代表**恢复成功率**:两个策略都成功恢复,且都**恰好修改 1 次**(没有反复重启)。

### 成本对比(LLM 的代价)

| 维度 | 规则策略 | LLM 策略 | 倍数 |
|---|---|---|---|
| 恢复耗时 | 5.3s | 12.4s | **2.3×** |
| 正常场景耗时 | 0.36s | 7.7s | **21×** |
| 工具调用(正常场景) | 1.0 | 4.4 | 4.4× |
| Token | 0 | 102,045(20 轮合计) | — |

规则策略快是因为它"知道答案":看一眼健康探针就知道该查 redis。
LLM 没有这个先验,它必须**真的去观测**(健康 → api 状态 → redis 状态 → 日志)才能下结论 —— 这 4.4 次工具调用正是"自主诊断"的成本。

### 一个必须正视的问题:场景太容易,区分不出策略

两个策略都是 100%,说明**当前故障对 LLM 毫无挑战**。这份报告暂时只能证明"LLM 能用",不能证明"LLM 比规则强"。要让对照实验有信息量,需要加难度:

1. **增加候选根因** —— 同一症状(API 5xx)可能由 redis 挂、配置错、依赖超时引起,规则策略会失效,模型才有发挥空间。
2. **引入规则覆盖不了的分支** —— 例如"redis 在运行但响应极慢"、"容器反复重启"。
3. **加干扰项** —— 日志里的无关报错,考验模型的证据筛选能力。

## 六、已知局限

1. **样本小**:每格 5 轮,100% 通过率无法给出置信区间。
2. **单场景**:只有 1 个故障类型,`scenarios/` 的扩展性(新故障 = 加 yaml)尚未被验证。
3. **裁判深度有限**:只验证健康 + 一个缓存键,不检查系统内部状态(如 redis 配置是否被改坏)。
4. **LLM 无记忆**:每轮独立,不利用上一轮经验(未来可在 prompt 里注入历史手册)。
5. **未测失败恢复**:没有故意让 Agent 修不好的场景,`FAIL` 路径只在人工演示中验证过。
